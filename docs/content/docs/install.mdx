## Installation and setup

<Callout title="Prerequisite knowledge" type="info">
In this installation guide, we assume you are already familiar with setting up CKAN extensions on a CKAN instance.

The following resources can be helpful for additional info as a reference. We recommend first try going through this page's installation guide for your CKAN instance, and then refer to these documentation sources as needed:

- [CKAN - Extending guide](https://docs.ckan.org/en/latest/extensions/index.html)

You can also adapt the installation steps for your setup, such as modifying your Docker Compose or Kubernetes and Helm setup.

<Callout title="Minimum CKAN version 2.12" type="info">The ckanext-gztr CKAN extension **requires CKAN version 2.12 or above**.</Callout>

```bash
cd /usr/lib/ckan/default/src
. ../bin/activate
```

## Install ckanext-scheming

The ckanext-gztr extension relies on [ckanext-scheming](https://github.com/ckan/ckanext-scheming) to add the interactive gazetteer to the new dataset form.

<Callout title="Not using ckanext-scheming?">Technically ckanext-gztr can be used without ckanext-scheming, however it is likely that you may already be using ckanext-scheming and we recommend doing so.</Callout>

Run the following in `/usr/lib/ckan/default/src` to install the ckanext-scheming extension:

```bash
pip install -e "ckanext-scheming@git+https://github.com/ckan/ckanext-scheming.git"
```

Then in your CKAN config file (e.g., `/etc/ckan/default/ckan.ini`) for `ckan.plugins` add `scheming_datasets`. For example:

```ini tab="INI"
ckan.plugins = activity scheming_datasets
```

```dotenv tab="ckanext-envvars"
CKAN__PLUGINS="activity scheming_datasets"
```

<Callout title="What is scheming_datasets?" type="info">Adding `scheming_datasets` to your `ckan.plugins` value enables ckanext-scheming features for datasets. In particular ckanext-gztr can expose the [dataset publisher gazetteer](http://localhost:3000/docs/features#dataset-publisher-gazetteer) through this.</Callout>

Add the preset `ckanext.gztr:schemas/presets.yaml` to the end of your `scheming.presets` config value:

```ini tab="INI"
scheming.presets = ckanext.scheming:presets.json ckanext.gztr:schemas/presets.yaml
```

```dotenv tab="ckanext-envvars"
CKAN___SCHEMING__PRESETS=ckanext.scheming:presets.json ckanext.gztr:schemas/presets.yaml
```

<Callout title="What is a scheming preset?" type="info">[Presets](https://github.com/ckan/ckanext-scheming#preset) are sets of default values for certain field keys. What this allows for is using custom-defined HTML snippets such as the dataset publisher gazetteer in the dataset metadata form when publishing a CKAN dataset.</Callout>

**If you already have a running CKAN instance with ckanext-scheming installed and a custom dataset schema** then you'll want to add the following fields to your schema YAML file for the dataset publisher gazetteer to appear in the dataset metadata form:

```yaml
# ckanext-gztr fields
# Interactive React gazetteer widget
- field_name: gazetteer
  label: Indicate Spatial Coverage
  form_snippet: gazetteer_widget.html
  display_snippet: null
  validators: ignore_missing gazetteer_validator
  output_validators: scheming_load_json
# Full GeoJSON (without geometries for selected features)
# as a STAC ItemCollection (based on GeoJSON FeatureCollection)
# from user's selection in data publisher gazetteer
- field_name: spatial_full
  label: Geospatial metadata
  display_snippet: gazetteer_preview.html
  form_snippet: text.html
  form_placeholder: Filled in automatically as you select areas above.
# Where DataPusher Plus stores its metadata suggestions. Only needed if you
# use the DataPusher Plus integration described later on this page.
- field_name: dpp_suggestions
  label: DPP Suggestions
  preset: json_object
  form_snippet: null
  display_snippet: null
```

**If you do not have an existing dataset schema configured for your CKAN instance**, then you can add the following demo dataset schema to try out the gazetteer (e.g. right below the line with `ckan.plugins`) in the dataset metadata form:

```ini tab="INI"
scheming.dataset_schemas = ckanext.gztr:schemas/dataset.yaml
```

```dotenv tab="ckanext-envvars"
CKAN___SCHEMING__DATASET_SCHEMAS=ckanext.gztr:schemas/dataset.yaml
```
<Callout title="Customize for your use case!" type="warning">The `dataset.yaml` file however may not fit your use case, so ensure you use a separate schema as needed.</Callout>

</Step>

## Install ckanext-gztr

Install ckanext-gztr and its dependencies in your activated virtual environment:

```bash
cd /usr/lib/ckan/default/src
git clone https://github.com/dathere/ckanext-gztr.git
cd ckanext-gztr
pip install -U "setuptools>=77"
pip install -e .
pip install -r requirements.txt
```

<Callout title="Why upgrade setuptools?" type="info">`pyproject.toml` declares its license as a [PEP 639](https://peps.python.org/pep-0639/) license expression (`license = "AGPL-3.0-or-later"`), a bare string that setuptools only accepts from version 77 onwards. A CKAN source install on Ubuntu 24.04 ships an older setuptools, so `pip install -e .` fails with an `invalid pyproject.toml config` error for `project.license` until you upgrade. You can skip this step if you let pip build in an isolated environment, since `pyproject.toml` already requires `setuptools>=77` to build.</Callout>

Then add `gztr` to your `ckan.plugins` in your `/etc/ckan/default/ckan.ini` file:

```ini tab="INI"
ckan.plugins = activity scheming_datasets gztr
```

```dotenv tab="ckanext-envvars"
CKAN__PLUGINS="activity scheming_datasets gztr"
```

</Step>

## Install JTS and update the Solr schema file

### Brief overview of why we're going to install JTS and update `schema.xml`

With ckanext-gztr, one of the main features for public usage is geospatial search on the `/dataset` page of a CKAN web app by drawing a bounding box over a region.

<video style={{ borderRadius: "1rem" }} autoPlay muted loop controls={false} src="/media/nmwdc-public-gazetteer-search-demo.mp4" />

CKAN uses the open-source [Apache Solr](https://solr.apache.org/) for multi-modal search. With Apache Solr there are various ways to run a [spatial search](https://solr.apache.org/guide/solr/latest/query-guide/spatial-search.html). ckanext-gztr uses [a similar approach to ckanext-spatial](https://docs.ckan.org/projects/ckanext-spatial/en/latest/spatial-search) for spatial search, attempting to run a geospatial intersection filter by intersecting the user's drawn bounding box against each dataset's simplified spatial geometry field which is indexed. This spatial field is a geometry, often a `Polygon` or `MultiPolygon`, and is necessary to have the dataset searchable by location by having it indexed in Solr.

The dataset's `spatial_full` field is transformed into WKT geometry using the [shapely](https://shapely.readthedocs.io/en/stable/) Python library and named as `spatial_geom` in Solr as an indexed field. Then a geospatial search query is ran through the following `Intersects` operation against `spatial_geom` and the bounds of the user's drawn bounding box (mimicing the filter used by ckanext-spatial):

```js
{!field f=spatial_geom}Intersects(ENVELOPE({minx}, {maxx}, {maxy}, {miny}))
```

### Installation

However to run this geospatial search against polygons we need to install the [JTS](https://github.com/locationtech/jts) library for Solr and to configure it properly.

It may be a bit tricky to get JTS running with CKAN and Solr as intended. The CKAN development team [provides preconfigured Solr Docker images for CKAN](https://github.com/ckan/ckan-solr) which you can refer to as an example.

To install JTS, follow the steps listed in the following admonition.

<Callout title="Complete these steps in particular!" type="info">

**Follow [the Solr docs here](https://solr.apache.org/guide/solr/latest/query-guide/spatial-search.html#jts-and-polygons-flat)**, including these steps in particular:

1. **Install the JTS JAR file**
2. **Place the installed JTS JAR file in a specific location as mentioned in the linked docs** (e.g. `$SOLR_INSTALL/server/solr-webapp/webapp/WEB-INF/lib/` where `$SOLR_INSTALL` in the [official CKAN Solr spatial images](https://github.com/ckan/ckan-solr) is `/opt/solr/`).

</Callout>

For additional information see the Solr documentation for the latest documentation on how to install JTS [here](https://solr.apache.org/guide/solr/latest/query-guide/spatial-search.html#jts-and-polygons-flat).

**Now you'll need to update your Solr schema file**. Find the relevant sections as shown in the top-level tags below and add the sub-level content to them:

```xml
<!-- ... -->

<types>
  <!-- ... -->
  <!-- RPT field type for searching polygons with ckanext-gztr -->
  <fieldType 
      name="location_rpt" class="solr.SpatialRecursivePrefixTreeFieldType"
      spatialContextFactory="JTS"
      autoIndex="true"
      validationRule="repairBuffer0"
      distErrPct="0.025" 
      maxDistErr="0.001"  
      distanceUnits="kilometers">
  </fieldType>
</types>

<fields>
  <!-- ... -->
  <!-- Allow ckanext-gztr to index simplified geometry and place keywords -->
  <field name="spatial_geom"  type="location_rpt" indexed="true" stored="true" multiValued="true" />
  <field name="place_keywords" type="string" indexed="true" stored="true" multiValued="true"/>
  <!-- ... -->
</fields>
<!-- ... -->
<!-- Allows for searching by place keywords in the dataset search page by ckanext-gztr -->
<copyField source="place_keywords" dest="text" />
```

</Step>

## Set up the `gztr` storage

With CKAN 2.12 there are now [configurable storages](https://docs.ckan.org/en/latest/maintaining/filestore.html#setup-file-storages), which are objects that can store files in a local filesystem, cloud, database, or elsewhere. This allows you to customize where you want to store GeoParquet files that are used throughout your installation of ckanext-gztr.

Add the following lines to your CKAN configuration file and customize it as needed:

```ini tab="INI"
ckan.files.storage.gztr.type = ckan:fs
ckan.files.storage.gztr.path = /var/ckan/storage/uploads/gztr
ckan.files.storage.gztr.initialize = true # Creates the `gztr` directory if it doesn't exist
# ckan.files.storage.gztr.public = true # Optional, makes the files publicly downloadable. May not need this since the STAC API should be used instead.
```

```dotenv tab="ckanext-envvars"
CKAN__FILES__STORAGE__GZTR__TYPE=ckan:fs
CKAN__FILES__STORAGE__GZTR__PATH=/var/lib/ckan/storage/uploads/gztr
CKAN__FILES__STORAGE__GZTR__INITIALIZE=true
# CKAN__FILES__STORAGE__GZTR__PUBLIC = true # Optional, makes the files publicly downloadable. May not need this since the STAC API should be used instead.
```

The new `gztr` directory should be made in your filesystem at `/var/ckan/storage/uploads/gztr` once you run your CKAN instance. This is where the GeoParquet files will be stored, along with the `catalog.json` and `collections.json` files we'll set up soon.

<Callout title="Using S3 instead of the filesystem" type="info">If you prefer to use a cloud storage service that is S3-compatible, you can learn how to set up the `gztr` storage with an S3-compatible cloud storage adapter on the [CKAN file storages documentation](https://docs.ckan.org/en/latest/maintaining/filestore.html#setup-file-storages) (you may need to scroll down a bit) which uses the [ckanext-file-keeper-cloud](https://github.com/ckan/ckanext-file-keeper-cloud) CKAN extension. However note that with how ckanext-gztr is currently implemented, **there may be many calls to the S3 storage**, so you may want to periodically sync from an external S3 bucket to the filesystem storage instead.</Callout>

### Storing the files in S3

A local filesystem is not always durable. On Kubernetes, for example, `ckan.storage_path` is often an ephemeral volume, so anything uploaded to a `ckan:fs` storage disappears when the pod restarts and the gazetteer goes back to showing no features. For those deployments ckanext-gztr provides a `gztr:s3` storage that keeps the files in any S3-compatible bucket.

Install the extra dependency:

```bash
pip install "ckanext-gztr[s3]"
```

Then configure the storage with `gztr:s3` instead of `ckan:fs`:

```ini
ckan.files.storage.gztr.type = gztr:s3
ckan.files.storage.gztr.bucket = my-bucket
ckan.files.storage.gztr.path = gztr # Key prefix within the bucket
ckan.files.storage.gztr.region = us-east-1
ckan.files.storage.gztr.key = <AWS access key>
ckan.files.storage.gztr.secret = <AWS secret key>
ckan.files.storage.gztr.public = true
```

Set `ckan.files.storage.gztr.initialize = true` only if you want CKAN to create the bucket when it is missing, which requires credentials permitted to do so. Add `ckan.files.storage.gztr.endpoint` to point at an S3-compatible service other than AWS.

The `path` entry is a key prefix rather than a directory, so with the configuration above `config.json` is stored as the object `gztr/config.json`. Because the objects are read by their location, you can also place the files in the bucket directly, for example with `aws s3 cp`, instead of uploading them through CKAN.

<Callout title="Why not use ckan:s3 directly?" type="info">The `gztr:s3` storage builds on the `ckan:s3` storage from [ckanext-file-keeper-cloud](https://github.com/ckan/ckanext-file-keeper-cloud), and differs from it in one respect: it serves file content through CKAN rather than redirecting to a presigned URL on the bucket's own domain. The gazetteer widgets read these files with `fetch()`, so a cross-origin redirect would require a CORS policy on the bucket. Serving from CKAN's own origin avoids that, and keeps the behaviour the same as a `ckan:fs` storage.</Callout>

</Step>

## SpatioTemporal Asset Catalogs (STAC) with ckanext-gztr

The [STAC](https://stacspec.org) specification is a common language to describe geospatial information, which can help make geospatial data easier to use, index, and discover.

We make use of the STAC specification throughout ckanext-gztr, including both how data models are organized and for the STAC API endpoints that get added to your CKAN instance.

<Callout title="Helpful STAC resources" type="info">
If you're new to the STAC specification, here are a few resources you could get started with:

### Upload your preset GeoJSON `FeatureCollection` files

As a sysadmin you'll provide GeoJSON files that are used throughout ckanext-gztr including for the public search gazetteer, the dataset publisher gazetteer, and the place keywords search functionality.

<Callout title="Geospatial data sources" type="info">We provide guides on how to download and format data from various geospatial data sources in [the geospatial data section](/docs/geospatial-data) of this documentation. However **we still recommend reading through this section first** to understand how you can add custom geospatial collections for your CKAN instance.</Callout>

The GeoJSON files must be in a specific format so that ckanext-gztr can properly use them. Here are the conditions followed by an example GeoJSON file:

- A GeoJSON file must be a [`FeatureCollection`](https://datatracker.ietf.org/doc/html/rfc7946#section-3.3) using WGS84 as its geographic coordinate reference system.
- Each [`Feature`](https://datatracker.ietf.org/doc/html/rfc7946#section-3.2) must have a **unique** `id` entry. The value of the `id` entry is **unique across all `Feature`s in the `FeatureCollection`**. Therefore we do not recommend using a label such as a name for the ID, but rather a unique string or number such as basing the `id` on an existing unique ID system for the `FeatureCollection`.
- Each `Feature` must also have a `title` entry in its `properties` dictionary where the value of `title` is a human-readable name for the `Feature`, such as a county name.

<Callout title="Unique ID is required!" type="warning">Make sure that each `Feature` in a `FeatureCollection` has a unique ID. This is required for ckanext-gztr to work properly. If you have multiple geospatial Polygon `Feature`s that are meant to be selected as one feature (e.g. a group of cities) then you may need to consolidate them into one `Feature` with a `MultiPolygon` geometry.</Callout>

Here we provide a truncated part of a GeoJSON file `Public_Water_Systems.geojson` for NMWDC with data provided by [Geoconnex](/docs/geoconnex-integration) (we omit the value for `coordinates` here as it would be too long):

```json
{
  "type": "FeatureCollection",
  "features": [
    {
      "type": "Feature",
      "properties": {
        "pws_id": "063500110",
        "title": "JEMEZ PUEBLO", // [!code highlight]
        "source_url": "https://www.hydroshare.org/resource/b11b8982eebd4843833932f085f71d92/data/contents/temm.geojson",
        "data_source": "SimpleLab",
        "geoconnex_uri": "https://geoconnex.us/ref/pws/063500110"
      },
      "id": "063500110", // [!code highlight]
      "geometry": {
        "type": "MultiPolygon",
        "coordinates": [...]
      }
    },
    ...
  ]
}
```

Notice that the ID is based on an existing ID system for public water systems in the USA provided by the EPA as described in `collections.json`. We also have `title` in the `properties` of the `Feature` which is a human-readable name describing the feature. You can add [other common metadata](https://github.com/radiantearth/stac-spec/blob/master/commons/common-metadata.md) such as a `description` and `geoconnex_uri` as described in the [Geoconnex integration](/docs/geoconnex-integration) documentation.

You'll now need to upload the GeoJSON file to your `gztr` storage through the `gztr_collection_create` custom CKAN API Action endpoint which converts your GeoJSON file into a GeoParquet file. Since we're using the CKAN API, you should ensure your CKAN instance is running.

Here is an example of uploading a GeoJSON file `NM_HUC8_Sub_Basins.geojson` through the CKAN API using `curl` in a Bash shell:

```bash
read -p 'CKAN sysadmin API Token: ' api_token
curl -H "Authorization: $api_token" -X POST -F upload=@./NM_HUC8_Sub_Basins.geojson -F storage=gztr http://localhost:5000/api/3/action/gztr_collection_create
```

Here is the output that is returned:

```json
{
  "help": "http://localhost:5000/api/3/action/help_show?name=gztr_collection_create",
  "success": true,
  "result": {
    "name": "nm_huc8_sub_basins.parquet",
    // [!code word:nm_huc8_sub_basins]
    "location": "nm_huc8_sub_basins.parquet", // [!code highlight]
    "storage": "gztr",
    "content_type": "application/octet-stream",
    "size": 6394247,
    "hash": "91437835777a3e23633d36a0021c004e",
    "algorithm": "md5",
    "created": "2026-08-18T09:32:52.751045+00:00",
    "storage_data": {},
    "id": "a13a09bc-8694-40f8-a082-bc6bca0c21a7",

```

Now **copy the `location` stem** that is returned after uploading because we will use it for later, for example `nm_huc8_sub_basins` (case-sensitive! notice the file name is not exactly the same as the original GeoJSON file). Do this for each file you upload, as you'll need the value for when you define your STAC Catalog and STAC Collections in the next steps.

### STAC Catalog (`catalog.json`) and STAC Collections (`collections.json`)

We need to define metadata about the geospatial data that is being stored by the CKAN instance and exposed through the STAC API. You'll need to define a [STAC Catalog](https://github.com/radiantearth/stac-spec/blob/master/catalog-spec/catalog-spec.md) as a `catalog.json` file which is a top-level description of your the geospatial data available from your CKAN instance using STAC. You'll also need to define a file `collections.json` that defines the [STAC Collections](https://github.com/radiantearth/stac-spec/blob/master/collection-spec/collection-spec.md) available from your STAC API.

We provide truncated examples in the clickable accordions below.

  ```json

      "providers": [
        {
          "name": "U.S. Environmental Protection Agency (EPA)",
          "description": "Independent agency of the United States government focused on environmental protection concerns.",
          "roles": [
            "producer"
          ],
          "url": "https://epa.gov"
        },
        {
          "name": "Geoconnex",
          "description": "Geoconex Reference API hosting the public water systems geospatial data. The public water systems for New Mexico are a subset of the data hosted by Geoconnex.",
          "roles": [
  ```

### Upload `catalog.json` and `collections.json` to the `gztr` storage

Now that you have your STAC Catalog and STAC Collections files prepared, you'll need to upload them to the `gztr` storage.

Here is an example of uploading the `catalog.json` and `collections.json` files through the CKAN API using `curl` in a Bash shell (make sure you use a sysadmin's API token):

```bash
read -p 'CKAN sysadmin API Token: ' api_token
curl -H "Authorization: $api_token" -X POST -F upload=@./catalog.json -F storage=gztr http://localhost:5000/api/3/action/file_create
curl -H "Authorization: $api_token" -X POST -F upload=@./collections.json -F storage=gztr http://localhost:5000/api/3/action/file_create
```

## Optional: metadata suggestions with DataPusher Plus

The dataset schema shipped with ckanext-gztr opts several fields into [DataPusher Plus](https://github.com/dathere/datapusher-plus) (DP+) metadata suggestions. When a publisher uploads a resource, DP+ profiles the file and offers one-click suggestions for fields such as Description, Spatial Description, Coordinate System, Update Frequency and Primary Key Field. This step is entirely optional — the gazetteer works without it.

Suggestions come from two independent sources:

- **DRUF formulae** (`suggestion_formula` in the schema) are Jinja2 templates evaluated against the profiling statistics DP+ collects. These need no AI service.
- **AI suggestions** (`ai_suggestion: true` in the schema) come from `qsv describegpt`, which calls an OpenAI-compatible LLM endpoint.

Both write into the `dpp_suggestions` field, so your dataset schema must declare it (the schema at `ckanext.gztr:schemas/dataset.yaml` already does):

```yaml
- field_name: dpp_suggestions
  label: DPP Suggestions
  preset: json_object
  form_snippet: null
  display_snippet: null
```

Install DP+ following [its own installation guide](https://github.com/dathere/datapusher-plus), then add `datapusher_plus` to `ckan.plugins` and set the following in your CKAN config file:

```ini
ckanext.datapusher_plus.enable_druf = true
ckanext.datapusher_plus.enable_form_redirect = true
ckan.datastore.sqlsearch.enabled = true
```

`enable_druf` turns on the resource-upload-first flow, where a publisher uploads their data before filling in metadata so that suggestions are ready by the time the metadata form opens. ckanext-gztr overrides the resource form in that flow to offer a **Save & Fill Metadata** button. `ckan.datastore.sqlsearch.enabled` is required by the Update Frequency formula, which queries the DataStore to infer how often the data is updated.

To also enable AI suggestions, set:

```ini
ckanext.datapusher_plus.enable_ai_suggestions = true
```

The LLM endpoint itself is configured for `qsv` rather than for CKAN, so export these environment variables in the same environment that runs the DP+ worker:

```bash
export QSV_LLM_BASE_URL="https://openrouter.ai/api/v1"
export QSV_LLM_MODEL="google/gemini-2.5-flash"
export QSV_LLM_APIKEY="<your API key>"
```

<Callout title="AI suggestions need an endpoint" type="warning">If `enable_ai_suggestions` is `true` but no LLM endpoint is configured, the AI suggestion buttons still render on the form and simply never produce a value. The DRUF formula suggestions are unaffected.</Callout>
